# Feature-Parity Checklist

- Area: Acceptance ledger for SurveyJS feature parity
- Status: proposed
- Owner: Jarod
- Last updated: 2026-08-02

This is the authoritative acceptance document for the project's overall AC. A row is
**green only when the named proof passes in CI** — a host-demo scenario, rendering
integration test, or unit suite exercised through public APIs (see the
[guidelines](./library-development-guidelines-details.md)). Never flip a row by
assertion.

Parity target is the SurveyJS **Form Library** and **Survey Creator** as documented
in 2026 (v2/v3 era). Items on SurveyJS's own 2026 roadmap that have not shipped as
core parity surface are tracked in §O as *watch* items, not acceptance items.

Proof naming convention: `parity/<row-id>-<slug>` (e.g. `parity/B3-visible-if`).

**Demo coverage rule.** A closed row carries a host-demo scenario whenever the
capability is observable in the running application. Where it is not, the row says so
and why. Unit coverage alone is the exception, not the norm — the demo is what proves
the capability through the same boundary a consumer uses, and it has repeatedly caught
what unit tests could not: a numeric answer that rendered blank, an API wart, a
placeholder that never cleared.

> **Vocabulary caveat (added 2026-08-02).** This checklist was derived from SurveyJS's
> documented surface and therefore uses their property and type names throughout —
> `visibleIf`, `choicesByUrl`, `paneldynamic`, `matrixdropdown`, `questionsOnPageMode`,
> `storeDataAsText`, and so on. Since
> [ADR-0001](./adr/0001-own-definition-format.md) established that our definition
> format is **our own**, those names describe the **capability a row demands, not the
> name our format must use**. Do not treat a name in this document as a naming
> requirement — read every identifier here as "the capability SurveyJS calls X".
>
> These rows are restated **incrementally**: when a PR declares the corresponding
> property in the metadata registry, that same PR rewrites the row in our own
> vocabulary. There is no separate rename pass, because naming properties in this
> table ahead of the registry would invert the design order ADR-0001 sets. This banner
> is removed once §A–§N are clean, and its presence is the outstanding-work marker.
>
> **Still present at Phase 1 exit, deliberately.** §A–§E are closed, but §F–§N have not
> been built and their rows still carry SurveyJS's names throughout. Removing the banner
> now would claim a vocabulary migration that has only happened for the sections that
> shipped.

## §B — Expressions & conditional logic

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| B1 | Expression language: literals, `{question}` refs incl. composite paths (`{matrix.row.col}`, `{panel[0].q}`), arithmetic, comparison, and/or/not, contains/anyof/allof, empty/notempty | ☑ | `parity/B1-expression-grammar` (precedence/associativity via print round-trip) + `parity/B1-operators` (evaluation), unit, through public API. Not demo-testable: precedence, associativity and error recovery have no user-visible surface — the demo exercises the language's *use* in every other scenario |
| B2 | Built-in function library (iif, sum, avg, min, max, count, age, today, currentDate, getDate, diffDays, ...) + custom sync and async function registration | ☑ | `built-in function library` for the library, `parity/B2-async-functions` (unit + demo) for registration. Building this found that **a host had no way to register a function at all** through `parseSurvey` — the sync half was reachable only by calling the evaluator directly, which no host does — so both halves now arrive through the parse options. The evaluator stays synchronous: an expression is evaluated inside a dependency transaction, and one that stopped to await would leave every rule after it unevaluated and the model part-way through a cascade. So an async call yields `undefined` this time round — which every operator already treats as an unanswered question, so no operator needed a third state — the work starts, and the rules run again when it lands. **The result cache is load-bearing, not an optimisation**: without it each re-evaluation starts the call again and each call triggers another re-evaluation, and the mutation proving that hung the harness rather than failing it. Keyed on name *and* arguments. A rejection is reported at the call site's own span and not retried, so a broken endpoint is not a request storm. One namespace, checked in both registration orders. **Worth knowing:** every async function is called once at startup with whatever its arguments are then, so a lookup that costs something should return early for an argument it cannot use — the demo's does |
| B3 | `visibleIf` on questions, panels, pages, and individual choices | ☑ | `parity/B3-visible-if`, `parity/B3-visible-if-choice` (questions, pages, choices) and `parity/E1-panel-visibility` (panels, unit + browser + host E2E). A hidden panel takes its subtree out of reach without marking each child invisible — reachability and visibility are different questions, and only the first one is the container's to answer |
| B4 | `enableIf` / `requiredIf` | ☑ | `parity/B4-enable-if`, `parity/B4-required-if` (unit, browser, host E2E). Scope of `requiredIf`: questions, the only element that holds an answer. `enableIf` now also applies to panels, proven by `parity/E1-panel-enable` — the renderer uses a `fieldset`, so a disabled group freezes its subtree natively rather than by walking children |
| B5 | `setValueIf` + `setValueExpression`, `resetValueIf`, `defaultValueExpression` | ☑ | `parity/B5-default-value-expression` (unit + host E2E), `parity/B5-set-value-if` and `parity/B5-reset-value-if` (unit + host E2E). Precedence reset > set > default is defined in `createValueRule`, not left to graph ordering |
| B6 | Calculated values (survey-level `calculatedValues`, usable in expressions and completed HTML) | ☑ | `parity/B6-calculated-values` (unit + host E2E) covers computation, chaining, use from question expressions, and `includeIntoResult`; `parity/B6-calculated-values-in-completed-html` (unit) and `parity/E5-completion-flow` (demo) close the completed-HTML half, which had nowhere to be proven until E5 existed. A completed page reads a calculated value and an answer through the same placeholder and cannot tell them apart — including a value *not* marked `includeIntoResult`, because what an ending says is a different question from what gets submitted |
| B7 | Triggers: complete, setvalue, copyvalue, runexpression, skip | ☑ | `parity/B7-trigger-complete`, `-setvalue`, `-copyvalue`, `-runexpression`, `-skip` (unit); host E2E for all five. Triggers fire on the transition into true, not while it holds. `skip` became demo-testable once the renderer paginated (§E2): `parity/B7-trigger-skip` moves the respondent back a page and the renderer follows |
| B8 | Dependency graph: value change re-evaluates only dependents; cycles detected and reported | ☑ | `parity/B8-dependency-graph` (selective re-evaluation, ordering), `parity/B8-cycle-reporting` (participating nodes named), `parity/B8-pattern-edges` (dynamic collections), unit, through public API. Not demo-testable: "only dependents re-evaluated" is by definition invisible, and proving cycle reporting would mean authoring a broken survey into the demo |
| B9 | Carry-forward choices (`choicesFromQuestion`, selected/unselected modes) | ☑ | `parity/B9-carry-forward-choices` (unit + host E2E). The carried list is a live view, not a snapshot, so a source choice hidden by its own `visibleIf` disappears here too. Shares `ChoiceSourceController` with B10, so both dynamic sources resolve through one object |
| B10 | REST choices (`choicesByUrl`: url/path/valueName/titleName, caching, url with `{question}` placeholders) | ☑ | `parity/B10-rest-choices` (unit + host E2E). Placeholders become real graph dependencies, so an answer change re-fetches. The fetcher is injected — core is I/O-free and cannot reference `fetch`. The demo calls a live public API; the E2E intercepts it so CI never depends on a third party. A superseded response cannot install itself over a newer one (request generations, proven by mutation), the cache is keyed on the conversion settings and not the URL alone, and one in-flight request is shared by every source awaiting it. The original typed value survives the renderer, so a numeric `id` records as a number. Definitions carry origin-relative URLs and the host resolves the origin in `fetchJson`, so one definition promotes across environments unedited ([ADR-0017](./adr/0017-choices-url-environment-portability.md)); the demo's absolute URL demonstrates a public third-party API, not deployment portability. **Gaps noted:** the model carries no loading flag, so a renderer cannot show a loading state; multi-origin definitions are B11 |
| B11 | Deployment variable scope: `{@name}` placeholders resolved from host-supplied endpoints, distinct from the answer scope | ☑ | `parity/B11-deployment-scope` (unit). Built to [ADR-0017](./adr/0017-choices-url-environment-portability.md): substituted **verbatim** because it is a URL prefix and not a value, while an answer in the same URL is still percent-encoded — opposite treatment on purpose, since an encoded origin is a broken request and an unencoded answer is a way to reach a different host. Never a graph dependency: it is constant for the session. A separate namespace, so collision with a question name is impossible by construction. An undeclared name is a **parse diagnostic at error severity** — and, a test found, that alone was not enough: substituting the empty string left `/users`, which the fetcher then sent to the app's own origin, so a URL naming an origin nobody supplied is now not fetched at all. The template round-trips; the resolved origin never serializes. **Unproven guard:** the filter keeping `{@name}` out of the dependency graph. Its effect is a graph node that never fires, which has no observable behaviour — the mutation removing it survives, and inventing a test that could see it would be testing the test |

## §C — Question types: core

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| C1 | text — all inputTypes (text, number, email, date, datetime-local, time, tel, url, color, range, password), min/max, step, ~~maskSettings~~ | ☑ | `parity/C1-input-types`, `parity/C1-text-bounds`, `parity/C1-numeric-answers-are-numbers` (unit + demo) cover every input type, `min`/`max`/`step`, and the rule that a numeric input stores a number rather than the string the DOM reported. **`maskSettings` is dropped from parity scope**, not deferred ([ADR-0018](./adr/0018-input-masking-out-of-scope.md), 2026-08-02): masking is a caret-management problem wearing a formatting problem's clothes, the model already owns the part that matters — what reaches `data` is a typed value either way — and a host that needs one plugs in a library through the renderer seam rather than taking a nearly-right implementation from us. This is the **first named gap against the SurveyJS Form Library**, and it is stated here rather than implied by a row that looks complete |
| C2 | comment (multi-line, autoGrow, character counter) | ☑ | `parity/C2-comment` (unit + demo), `parity/C2-comment-auto-grow` (demo, measuring real height in Chromium). The budget is enforced by the model, not just displayed: a trigger or a restored `data` payload can exceed a `maxlength` attribute |
| C3 | radiogroup (choices, otherItem, noneItem, showClearButton, colCount, choicesOrder) | ☑ | `parity/C3-radiogroup` (unit), `parity/C3-C4-select-questions` (host E2E), browser proof for selection. `choicesOrder` supports none/asc/desc; random is deferred as it would make the suite non-deterministic |
| C4 | checkbox (selectAll, none, other, maxSelectedChoices, colCount) | ☑ | `parity/C4-checkbox` (unit), `parity/C3-C4-select-questions` (host E2E), browser proof for multi-select |
| C5 | dropdown (search/filter, lazy loading, placeholder, showOtherItem) | ☑ | `parity/C5-dropdown` (unit + browser) for single-select, placeholder and showOtherItem; `parity/C5-lazy-loading` and `parity/C5-lazy-search` (unit + demo) for paging. The host supplies a `loadChoicePage` loader — a callback rather than a URL template, because paging needs an offset, a size and a term against an API only the host knows the shape of, and core carries no I/O. Pages **accumulate**: the respondent is looking at page one, and a list that emptied itself to show more would lose their place. The end of the list is what the host reports rather than what a short page implies — a server-side match can legitimately be thin — and a mutation that inferred it from the page length is killed by a loader that under-fills. Search goes to the host, because the matching entry may never have been loaded; a reply for a term the respondent has typed past is discarded, proven by answering the requests out of order. A page that fails to arrive leaves the list usable and retryable rather than loading forever. Pagers outlive rule registration, which is rebuilt whole on every tree change. **The scroll trigger is an explicit control, not a sentinel**: a native `<select>` has no scroll to observe and infinite scroll reaches nobody who is not pointing at the list — Phase 2's combobox adds the scroll trigger alongside the button, never instead of it. The searchable combobox *UI* stays deferred to that a11y pass; the filter is a labelled search field beside a native list |
| C6 | tagbox (multi-select dropdown with search + lazy load) | ☑ | `parity/C6-tagbox` (unit + browser in real Chromium, proving the native adapter preserves the model's invariants) and `parity/C6-lazy-tagbox` (unit). The adapter reports its whole selection and the model decides what that means, so none-exclusivity and `maxSelectedChoices` hold however the selection was made. Paging lives on `SelectQuestion` rather than on either subclass, so a tagbox pages on identical terms — and an answer survives a filter that hides the choice naming it, because what someone chose is not a function of what the list is currently showing. The DOM half is C5's: one renderer is registered for both types. The combobox UI is deferred with C5 |
| C7 | boolean (switch + radio render modes, labelTrue/False, valueTrue/False) | ☑ | `parity/C7-boolean` (unit), `parity/C7-boolean-switch` and `parity/C7-boolean-radio-with-custom-values` (demo). Unanswered is a third state, not `false`: "was never asked" and "did not agree" are different facts and only the model can keep them apart |
| C8 | rating (numeric, stars, smileys, rateValues, min/max descriptions, display mode auto-switch) | ☑ | `parity/C8-rating` (unit), `parity/C8-rating-stars` and `parity/C8-rating-auto-collapses-a-long-scale` (demo). Stars and smileys are `aria-hidden` decoration over real radios, so the scale announces "4" rather than "star star star star"; `auto` collapses at eleven steps, and the collapsed form is a labelled control rather than a group so the select has a name of its own |
| C9 | ranking (drag reorder, selectToRankEnabled, keyboard support) | ☑ | `parity/C9-ranking`, `parity/C9-select-to-rank`, `parity/C9-reorder-primitive` (unit); `parity/C9-keyboard-reorder` (browser, in real Chromium); `parity/C9-drag-reorder`, `parity/C9-keyboard-reorder`, `parity/C9-select-to-rank` (demo, with a real pointer drag). Built as a **reusable interaction** rather than as ranking code, per [ADR-0009](./adr/0009-creator-drag-and-drop.md) constraint 3: `moveWithin` is the list arithmetic in core, `useReorder` the pointer-and-keyboard adapter in `@kajay/react`, and neither knows what is being reordered — Phase 3's Creator extends this instead of introducing a second drag system. Pointer events throughout, never HTML5 drag-and-drop, which has no keyboard story. The model is updated *during* a drag, so what is on screen mid-gesture is the answer as recorded rather than a preview that could disagree with it. Space or Enter picks a row up, the arrows move it, Escape puts it back, and every step is announced with its position and the total — a row sliding past its neighbours is otherwise entirely invisible. Mutation proved the arrow keys must be claimed (an unclaimed arrow scrolls the page out from under the respondent) and disproved an explicit refocus, which changed nothing because React already moves the focused element when rows are keyed by identity. An untouched ranking records **no answer**: the presented order is the author's, and banking it as agreement would put an opinion in the data that nobody expressed. **Unproven guard:** the pointer-id check that stops a second finger ending someone else's drag — there is no multi-touch harness here to demonstrate it |
| C10 | imagepicker (single/multi, imageFit, contentMode image/video) | ☑ | `parity/C10-imagepicker` (unit + demo). The one select type whose **arity is a property** rather than its type — everywhere else the split is a design-time fact, which is why those semantics live in two base classes. `applySelection` is the single point where the switch happens; a `select` override alongside it changed nothing, which a mutation test proved by surviving its removal. The choice text is every tile's accessible name whether or not `showLabel` draws it: a grid of unlabelled pictures is not an answerable question for anyone who cannot see them |
| C11 | multipletext (items, itemSize, per-item validation) | ☑ | `parity/C11-multipletext`, `parity/C11-multipletext-per-item-validation` (unit + demo). The answer is one object under the question's name, so `{address.city}` reaches a single field with nothing added — the path resolver already walks dotted references. Errors carry a `path` naming the field that earned them, which is what lets a renderer put the message beside the input instead of prefixing every line with a label the field already shows; §F's matrix cells want the same — and now use it. **Two defects surfaced while building F1**, both fixed here: an untouched multipletext reported none of its required items (the question was empty, so the check stopped before reaching them), and a message reported against the question as a whole had no slot to render into. Both are pinned by named tests |
| C12 | html (display), image (display), expression (read-only computed with displayStyle/format) | ☑ | `parity/C12-display-elements`, `parity/C12-expression-question` (unit); `parity/C12-html-and-image`, `parity/C12-expression-question` (demo). `html` and `image` descend from a new `displayelement` base rather than from `question`, so the Creator's generated property grid never offers `isRequired` on a paragraph of text. **Markup is rendered as markup** — that is the feature — so a definition is code at the host's level of trust; a host taking definitions from untrusted authors passes `sanitizeHtml` to `<Survey>`, and none ships here because a sanitizer that is nearly right is worse than none. `expression` formats through a fixed `en-US` locale so the same definition reads the same everywhere; making that follow the survey locale is §J |

## §D — Validation

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| D1 | Required with custom `requiredErrorText`; `isRequired` on any type incl. matrix rows | ☑ | `parity/D1-required` (demo + browser + unit) for every question type; `parity/F1-matrix-required` (unit) for matrix rows, where `isAllRowRequired` demands each visible row and the authored `requiredErrorText` applies to the row, because the row is what asked for an answer. `requiredIf` reaches the same gate as `isRequired`. ## §E — Navigation, flow & state

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| E1 | Pages, panels (nested, collapsible, visibleIf), elements ordering | ☑ | `parity/E1-panels`, `parity/E1-panel-visibility`, `parity/E1-panel-enable`, `parity/E1-panel-collapse` (unit, browser, host E2E). Panels nest arbitrarily and round-trip. A page is deliberately **not** a page element — parenting it under the same base would have made a page a legal child of a page, which the contract caught. Collapsing lives on the model, not in React: the definition declares the starting state and the Creator has to edit it. Only a panel that authored `state` is collapsible; one left at the default is a grouping device, and a toggle would invite hiding content the author never meant to hide |
| E2 | Prev/next/complete flow; page visibility recalculation; questionsOnPageMode (standard, singlePage, questionPerPage) | ☑ | `parity/E2-navigation`, `parity/E2-page-visibility`, `parity/E2-questions-on-page-mode` (unit, browser, host E2E). Every index counts **visible** pages, so a hidden page is not somewhere a respondent can stand. Hiding the page underneath a respondent clamps to the last visible one and announces the move, rather than leaving the renderer drawing nothing. `questionsOnPageMode` reshapes what navigation and the renderer see while leaving the authored `pages` untouched, and the reshaped list is memoised on its structure so React does not remount every question per render |
| E3 | Progress bar (pages, questions, correct-answer variants) + TOC navigation | ☐ | Partial: `parity/E3-progress` (unit), `parity/E3-progress-and-toc` (demo). `showProgressBar` (off/top/bottom/both), `progressBarType` (pages/questions/requiredQuestions) and `showTOC` are built. Measurement is a **pure function over the survey** exported from core, so the renderer gained no model surface and the arithmetic is testable without a DOM. `pages` counts what is **behind** the respondent — the page they are looking at is not finished, and the flattering alternative tells someone they are done with a page of questions still in front of them. Unreachable questions are not in the total, or progress would fall as branches opened. Nothing to answer counts as nothing outstanding, because an empty bar on a form that cannot be advanced is the more misleading lie. A native `<progress>` with a text label, since "two thirds" is a shape and "2 of 3 pages completed" is the fact that survives being read aloud. The TOC is a labelled `<nav>` of buttons with `aria-current`, and jumping **does not run the validation gate** — a contents list is for looking around, and refusing to let someone glance at page four because page two is incomplete makes it useless exactly when it is most wanted. **The correct-answer variant is not built**: it needs `correctAnswer`, which belongs to E8 and moves with it to Phase 2 |
| E4 | Preview mode before complete (showPreviewBeforeComplete, edit-from-preview) | ☑ | `parity/E4-preview` (unit + browser + demo). Preview is a **survey state**, not a flag beside the others, and that is what makes it read-only by construction: the survey reports itself read-only while previewing, so every question already is and no renderer is told to make it so — a mutation removing that one clause is killed by the model, not by the DOM. It draws the real question renderers rather than a summary table: an answer shown in a different control from the one it was given in invites a misreading, and a table needs its own formatting per question type, which is where the table and the form start to disagree. The last page's validation gate runs **before** the preview, so nobody reviews answers the survey is about to refuse. Edit returns to the page they left rather than the first one — a preview that costs a respondent their place is one they learn not to open. `showAnsweredQuestions` leaves out what nobody touched, and unreachable questions are never reviewed because they were never asked. A `complete` trigger still ends the survey outright: it says complete, not "ask them again" |
| E5 | Completed page (completedHtml, completedHtmlOnCondition), loading/empty states | ☑ | `parity/E5-survey-state`, `parity/E5-completed-html` (unit + browser); `parity/E5-completion-flow`, `parity/E5-completed-html-on-condition` (demo). What the survey is doing is **one value**, not a handful of flags — loading, empty, running, completed — because a renderer has to draw exactly one thing and two booleans let it be asked to draw a completed page for a survey that is still loading. Loading outranks everything (while the host says the model is arriving, nothing else it says is settled) and E4's preview is a state, not a flag beside them. `completedHtmlOnCondition` is an ordered list and the first match wins; a broken condition selects nothing rather than everything, because the wrong ending is worse than the default one. **Placeholders are escaped before they reach the markup**: the template is the author's and is meant to be markup, the value is the respondent's and is never trusted — unescaped, this is stored XSS on every survey that greets someone by name, and a mutation proves both halves. The authored markup round-trips whatever the conditions currently say. Default wording lives in the renderer, not the model, so it never reaches a definition; §J moves it to the string dictionary |
| E6 | Partial save/resume: serialize `data` + currentPageNo; onValueChanged/onCurrentPageChanged seams; sendResultOnPageNext pattern | ☑ | `parity/E6-save-and-resume`, `parity/E6-save-seams` (unit); `parity/E6-save-and-resume` (demo, through a **real page reload**). `survey.progress` is a plain-JSON snapshot and `survey.restore` applies it. **The page is remembered by name, not by index** — a deliberate departure from the row's own wording: add a page, reorder two, or let different answers make different pages visible, and index 2 is somewhere else, so a resumed respondent lands on a page they have never seen with nothing to say anything went wrong. A name either still exists or does not, and a page that no longer does leaves them at the start rather than nowhere. Answers restore **before** the page, because page visibility is computed from them — navigating first aims at a page that has not appeared yet, which a mutation reversing the order duly proves. Calculated values are recomputed rather than stored: writing one back would put a value in the response that nothing computed. The two save seams are the existing events, and what a host reads on `onCurrentPageChanged` already names the page they arrived at. The demo stores to `sessionStorage` and clears on completion — resuming into a survey already submitted invites a second submission — and treats a stored snapshot as untrusted input, since it may predate the definition it is being applied to |
| E7 | Read-only / display mode for the whole survey and per question | ☑ | `parity/E7-read-only` (unit + browser + demo). `question.isReadOnly` combines the survey-wide flag and the question's own, in the model — leaving that to each adapter is how one renderer honours the survey flag and another only the per-question one. It reaches the question through the **value host** seam, so `Question` still never imports `Survey`. **Read-only is not disabled**: the value keeps its place in the tab order, its focus and its announcement, which is exactly what someone reviewing what they submitted needs — `disabled` would take all three away. Native `readonly` where HTML defines it; `aria-readonly` on the group plus a refused change where it does not; and a read-only `<select>` offers only what was chosen, which is genuinely unchangeable rather than merely refusing. The refusal is on the **change handler, not the click**: cancelling a click's default stops the browser toggling a checkbox but not React reporting the change, which cost a failing test to discover. Programmatic writes still land, and that is the point — the demo's reference field is one nobody may type into and the engine fills in. **Not in scope for this row:** `readOnly` on a panel or page, which needs the container walk §F's composites will want anyway |
| E8 | Quiz mode: maxTimeToFinish, per-page timers, correctAnswer, quiz scoring, showTimerPanel | ☐ | **Phase 2** ([roadmap](./delivery-roadmap.md)), moved there 2026-08-02. It was in two places at once: named as out of scope for Phase 1 while Phase 1's exit gate asked for §E green. Nothing else in §E waits on it, so the gate moved rather than the work. It also carries a decision worth taking beside Phase 2's other timed features: timers put *time* in the model, core is I/O-free by rule, and a model that reaches for `Date.now()` makes every timed test a race — the clock has to be injected, as the expression engine's already is |
| E9 | Clear invisible values policies (onHidden, onComplete, none) | ☑ | `parity/E9-clear-invisible-values`, `parity/E9-reachability` (unit) for all three policies; `parity/E9-clear-invisible-values` (demo) for `onHidden`, the one you can watch happen. **Reachability, not the question's own visibility**: a question inside a hidden panel or on a hidden page is out of reach however visible it is itself, and a mutation swapping the two is killed by exactly that case. `onHidden` clears **inside the settle** that hid the question, so the first thing anyone hears about the change already has the answer gone — announcing a model where the question is unreachable and its answer is still in the data is what ADR-0004 exists to prevent. The sweep repeats until nothing more falls out, because clearing an answer can hide the question after it. Two authoring mistakes are survivable rather than fatal: a rule that refills what the policy clears is bounded by a pass cap, and one that *reads* the answer it refills — a stack of clears rather than a loop — by a re-entrancy guard on the after-settle hook. `onComplete` is the default and runs before `onComplete` fires, so the event never carries the data the policy exists to withhold. Disabled is not invisible: an `enableIf` chain leaves the answer alone, which the demo pins down |
| E10 | First-question autofocus, checkErrorsMode, goNextPageAutomatic | ☑ | `parity/E10-go-next-page-automatic` (unit), `parity/E10-autofocus` (browser); `checkErrorsMode` was built with D5 and is proven by `parity/D5-check-errors-mode` (unit + demo). Auto-advance applies only to questions a **single action finishes**, which the question type states about itself rather than a list kept elsewhere — a text answer arrives a character at a time, and a survey that turned the page after the first letter of a name would be unusable. It goes through the ordinary gate, so saving a click never skips a check, and unreachable questions do not hold the page back. **The last page never turns itself in**: submitting is a decision, and a survey that submitted itself on the final click would take it from the respondent along with any chance to look back. Autofocus is off by default and stays off — on a long page it drops a screen-reader user past the page title and any instructions above the first field, so doing it unasked is a bad default rather than a helpful one; both halves of that are tested. A trigger that writes the last one-step answer can also move the page, which is a caveat rather than a design: the model cannot tell a respondent's write from a rule's |

## §F — Matrix family

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| F1 | matrix (single-choice rows): columns/rows, isAllRowRequired, eachRowUnique, alternate rows | ☑ | `parity/F1-matrix`, `parity/F1-matrix-required`, `parity/F1-matrix-each-row-unique`, `parity/F1-matrix-definition` (unit); `parity/F1-matrix` (browser); `parity/F1-matrix`, `parity/F1-each-row-unique`, `parity/F1-alternate-rows` (demo). Rows and columns are **`itemvalue` collections**, not a shape of their own: a matrix row is a choice in every respect that matters — a value, display text, and a `visibleIf` the same engine evaluates — and a parallel type would have meant a second definition of the same thing for the registry, the Creator and every host to learn. That took generalizing choice conditions into `conditionalItems`, which each question type now answers for itself rather than being named in a list somewhere else. The answer is **one object keyed by row value**, exactly as a multipletext keys by field, so `{comparison.docs}` reaches a single row with nothing added and an emptied matrix collapses to `undefined` rather than lingering as a `{}` that no emptiness test would catch. Errors are reported **per row**: at most one per row and in row order, because a matrix with eight rows and one message at the top says that something is wrong and not where. `eachRowUnique` objects against the *second* row to use a column — the first is not the mistake, and marking it would send the respondent back to an answer they had just made. A hidden row is never asked for an answer nobody can give. In the DOM it is a real table: a cell is named by its row header **and** its column header, so it announces the question it is asking rather than its position in a grid — and a first attempt that put the error message inside the row header quietly pulled that text into every cell's accessible name, which a browser test caught. `alternateRows` puts a class in the markup and nothing else: the library ships no stylesheet, and shading is the host's decision (§I). **Gap noted:** a column that becomes invisible leaves any answer pointing at it in place — clearing it is E9's rule applied to a part of an answer, and belongs with the cell model in F2
| F2 | `matrixcells` — per-column question type (dropdown, checkbox, radiogroup, text, comment, boolean, expression, rating), column totals, cell visibleIf/enableIf with row context | ☑ | `parity/F2-matrix-cells`, `parity/F2-cell-conditions`, `parity/F2-column-totals`, `parity/F2-definition` (unit); `parity/F2-matrix-cells`, `parity/F2-cell-conditions`, `parity/F2-column-totals` (browser); `parity/F2-matrix-cells` (demo). **A column is a question, and a cell is an instance of it.** SurveyJS's `cellType` is simply `type` here — our format already has a word for what kind of thing something is — so a column is an ordinary question definition and each cell is a real question built from it by a registry-driven copy. That is the whole design: a `rating` in a table is the same model, the same validators and the same *renderer* as a `rating` on a page, including a host's own replacement for it, which a browser test pins down. The alternative — a bespoke cell object with a `cellType` switch — is a second, quietly diverging implementation of every question type. Cells are pointed at their slot through a value host, exactly as a page question is pointed at the survey, so nothing in `TextQuestion` knows a matrix exists. **Row context is resolved by rewriting, not by an evaluation scope**: `{row.price}` on the column becomes `{basket.docs.price}` on the cell, so the dependency graph sees statically what a cell condition reads and re-evaluates it in the same settle — an overlay in the evaluator would have hidden that from the graph. The definition keeps what the author wrote; only the cell carries the rewritten form. **Totals are declared on the matrix, naming the column** (`totals: [{ column, kind, format }]`), not on the column as SurveyJS does: our columns are questions, and a question has no business declaring a table footer — putting it there means a matrix-only property on every text field in every property grid forever. A column nobody answered totals to *nothing* rather than zero. Errors are reported twice on purpose — on the cell, where its own renderer draws them, and on the matrix with a `row.column` path, so the survey knows the table is unanswered. Building this found two defects invisible from the model: every cell of a column shared a DOM id (a browser points every label at the first match, so typing in row two wrote into row one), and every renderer read its value from `survey.getValue(name)` rather than from the question — which for a cell is nothing at all, and only looked right because React skips a DOM write it thinks is a no-op. Both are fixed with a named test each. **Not in scope here:** detail panels (F4) and `{row.col}` in *totals* expressions (F5)
| F3 | `matrixdynamic`: add/remove rows, min/max rows, confirmDelete, defaultRowValue, copy default from last row | ☑ | `parity/F3-matrix-dynamic`, `parity/F3-row-limits`, `parity/F3-row-defaults`, `parity/F3-dynamic-validation`, `parity/F3-definition` (unit); `parity/F3-matrix-dynamic`, `parity/F3-confirm-delete`, `parity/F3-row-limits` (browser); `parity/F3-matrix-dynamic` (demo). The same cells as F2, from the same base class; what differs is that **the rows are the answer** — an array of row objects — so the row count survives a save and resume with nothing stored beside it. A count kept anywhere else would be a second source of truth that disagreed the first time a host wrote `data`. An added row stays as `{}` even before anything is typed into it, because a respondent who pressed Add created something; rows below `minRowCount` are *implied* rather than stored, so an untouched matrix is still no answer at all rather than a page of blanks in the response. A new row is a **copy** of `defaultRowValue`, never the object itself: `data` goes to the host, and handing out the definition means a host tidying its results edits the survey it was given. A mutation proved that guard was unobservable until a test asked the question directly. `defaultValueFromLastRow` wins over `defaultRowValue` — it is the more specific statement. **`confirmDelete` is answered in the page, not with `confirm()`**: a native dialog cannot be styled or translated and is the control a respondent using a screen reader is most likely to lose their place in. **Known non-guard:** rebuilding cells after a *removal* is hygiene, not correctness — cells read their row live by index, so the answers move with them; what it prevents is graph rules accumulating for rows that no longer exist. The mutation removing it survives and the code says why rather than a test pretending otherwise
| F4 | Detail panels (expandable row detail with its own elements) | ☑ | `parity/F4-detail-panels` (unit + browser + demo). A detail element is a **cell like any other** — same builder, same row-scoped value host, same validation pass — drawn under the row instead of in a column, so a detail answer lands in the same row record and `{row.amount}` works in it unchanged. A table runs out of horizontal room long before a form runs out of questions, and this is where the long ones go. `underRowSingle` keeps one row open at a time. **A detail holding something invalid opens itself**: the respondent has just been told the page is wrong, and the field at fault was behind a closed panel — an error nobody can see is one nobody can fix. Which row is open is state the *model* holds, so another adapter can ask and the error rule has somewhere to live, but it is **not** announced on the event channel that carries answers: nothing in the survey depends on it, and the component that opened it is the one that re-renders. Expansion never serializes, for the same reason computed visibility never does
| F5 | Row/column expressions: `{row.col}` references, totals row with expressions | ☑ | `parity/F5-row-expressions`, `parity/F5-total-expressions`, `parity/F5-scope-rewriting` (unit); `parity/F5-row-and-total-expressions` (demo). **Every** expression a column carries is rewritten into the row's scope, not just its conditions: a computed `expression` cell, a `defaultValueExpression`, a `setValueIf`, and the expression of a validator hanging off the column. Which properties those are is now the **registry's** answer — properties declare `isExpression` — so one added later is covered by declaring itself rather than by being remembered in the cell builder, and §M's logic editor gets the same list for free. A cell's rules are ordinary graph rules with the cell's path as their declared write, so a computed cell settles in the *same transaction* as the answer that drives it rather than a render later. **Totals may be expressions**, computed in declaration order, where `{row.price}` means that column's own total — the same scope word one level up, because in both places `row` means "the record this belongs to". A total naming one declared after it sees nothing, which is the rule a spreadsheet applies and cheaper to explain than a second dependency graph for four numbers. A total that is broken, or that evaluates to something which is not a number, shows **nothing**: a figure under a column is read as a fact and there is no way to caveat one in a table cell. The row scope inside a total is an evaluator overlay rather than a rewrite, because a column total is not an answer and never will be — the one place where the honest answer is a local scope, and it is confined to a value computed on read that no rule depends on
| F6 | Responsive/mobile rendering mode for matrices | ☑ | `parity/F6-mobile-mode` (browser, for the explicit modes; demo **at a 375px viewport**, for `auto`). `mobileMode` is auto/table/list on all three matrix types, which are not related by inheritance — a phone is the same problem for each, and an author who learned the word on one should not find it spelled differently on the next. `auto` resolves against a **real media query**, subscribed rather than read once, so a resize and a rotation both land. That is the whole reason this row is not just a class name: the library ships no stylesheet, so a hook a theme might use would be a feature nobody could see, and a test asserting the hook would pass just as happily if it were wired to nothing. The breakpoint is in `rem`, so a reader who has turned text up runs out of room at the width they actually run out of room. The list layout is a **structural** change: each row becomes its own group with the row title as its legend, and the cells keep the labels they already have — which is why a cell is titled for its row *and* its column, a title that reads correctly under a legend and behind a column header alike. A single-select matrix gets the same treatment and needs it most: five columns of radio buttons in 375 pixels is a row of unlabelled dots. On a server there is no screen to ask, so `auto` renders the table — the layout that degrades to a scroll rather than to the wrong thing. **The browser suite now states a desktop viewport**: making layout depend on the window meant three table tests silently became list tests

## §G — Dynamic panels

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| G1 | paneldynamic: template panel, add/remove, min/max panels, panelCount binding | ☑ | `parity/G1-paneldynamic` (unit + browser + demo). **The same machinery as a dynamic matrix**, which is the whole result: a matrix row and a panel instance are both a record in an array holding instances of template questions bound to a local scope, so §F's builder, value host, scope rewriting and validation pass were extracted to `RepeatingQuestion` and this row is what is left over — the drawing. | G2 | Render modes: list, tab-per-panel/progress navigation modes | ☑ | `parity/G2-render-modes` (unit + browser). `list` draws every instance; `tab` gives a button per instance and `progress` a pair of arrows with a position — the same model state under two presentations, because which an author picks is a question about *how many* instances there will be rather than about what moving means. **Adding moves to what was added**: a control that creates something out of sight appears to do nothing. The position is clamped on **read**, not only where instances are removed — a host restoring a shorter response moves the ground under a stored index, and a mutation showed the write-side clamp hid that until a test wrote `data` directly
| G3 | Template expressions with `{panel.q}` scoping; valueName data binding/shared data | ☑ | `parity/G3-panel-scope`, `parity/G3-value-name` (unit); `parity/G3-panel-scope` (browser + demo). `{panel.q}` is F5's `{row.col}` under the word that reads better here — both mean "this record", and the scope word is the only thing the two types differ by. It is resolved the same way: rewritten into a real path (`{people[1].age}`) when the instance is built, so the dependency graph sees statically what a template condition reads. `valueName` is the data-binding half: a question's answer key, when it should differ from its name. Two questions sharing one share an answer — the same thing asked on two paths comes back as one field. Identity stays with `name`, because two questions that share an answer are still two questions; what follows the *answer* — clearing an unreachable one, re-checking a changed one — follows `valueKey`
| G4 | Nested composites: panels in dynamic panels, matrices in panels | ☑ | `parity/G4-nested-composites` (unit + browser + demo). Mostly the absence of a restriction: `templateElements` admits **page elements**, so a panel in a template is a panel and a matrix in one is a matrix, each drawn by whatever draws it anywhere else. Two things it did need. A repeating question created at runtime is handed the registry its own instances are built from — `parseSurvey` can only reach the questions on a page, and this one was created long afterwards. And conditions are registered for every *element* of an instance rather than every question, because a group carries a `visibleIf` and is not a question; without that a nested group was permanently visible. **A real defect surfaced in the demo E2E**: only the top element of an instance was being titled and given a unique key, so a question two levels down shared both with its twin in the next instance — the §F cell-id defect one level deeper, and the unit tests had missed it
