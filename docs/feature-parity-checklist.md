# Feature-Parity Checklist

- Area: Acceptance ledger for SurveyJS feature parity
- Status: proposed
- Owner: Jarod
- Last updated: 2026-08-02

This is the authoritative acceptance document for the project's overall AC. A row is
**green only when the named proof passes in CI** — a host-demo scenario, rendering
integration test, or unit suite exercised through public APIs (see the
[guidelines](./library-development-guidelines-details.md)). Never flip a row by
assertion.

Parity target is the SurveyJS **Form Library** and **Survey Creator** as documented
in 2026 (v2/v3 era). Items on SurveyJS's own 2026 roadmap that have not shipped as
core parity surface are tracked in §O as *watch* items, not acceptance items.

Proof naming convention: `parity/<row-id>-<slug>` (e.g. `parity/B3-visible-if`).

**Demo coverage rule.** A closed row carries a host-demo scenario whenever the
capability is observable in the running application. Where it is not, the row says so
and why. Unit coverage alone is the exception, not the norm — the demo is what proves
the capability through the same boundary a consumer uses, and it has repeatedly caught
what unit tests could not: a numeric answer that rendered blank, an API wart, a
placeholder that never cleared.

> **Vocabulary caveat (added 2026-08-02).** This checklist was derived from SurveyJS's
> documented surface and therefore uses their property and type names throughout —
> `visibleIf`, `choicesByUrl`, `paneldynamic`, `matrixdropdown`, `questionsOnPageMode`,
> `storeDataAsText`, and so on. Since
> [ADR-0001](./adr/0001-own-definition-format.md) established that our definition
> format is **our own**, those names describe the **capability a row demands, not the
> name our format must use**. Do not treat a name in this document as a naming
> requirement — read every identifier here as "the capability SurveyJS calls X".
>
> These rows are restated **incrementally**: when a PR declares the corresponding
> property in the metadata registry, that same PR rewrites the row in our own
> vocabulary. There is no separate rename pass, because naming properties in this
> table ahead of the registry would invert the design order ADR-0001 sets. This banner
> is removed once §A–§N are clean, and its presence is the outstanding-work marker.
>
> **Still present at Phase 1 exit, deliberately.** §A–§E are closed, but §F–§N have not
> been built and their rows still carry SurveyJS's names throughout. Removing the banner
> now would claim a vocabulary migration that has only happened for the sections that
> shipped.

| A7 | Typed event surface: onValueChanged, onComplete, onCurrentPageChanged, onValidate*, onUploadFiles, onDynamicPanelAdded, matrix row events | ☑ | `parity/A7-value-changed-event` (demo) for value/complete/page; `parity/D4-validate-question-event` and `parity/D3-async-validators` for the validation pair; `parity/A7-records-changed` and `parity/A7-files-changed` (unit) plus `parity/A7-model-events` (demo) for the three that had to wait for their features. **One channel for matrix rows and repeating-panel instances**, not two: §F and §G already share `RepeatingQuestion`, and a host reacting to rows almost always means instances — two channels is one of them forgotten the day a third repeating type arrives. Which kind it is, is a fact about `question`. Emitted from the model where the record actually changes, so a host hears it however the change was caused, and *not* from `invalidateCells`, which also fires for a rebuild that changed nothing: a locale switch throws every instance away, and announcing a row added because somebody switched to French is a lie a host acts on. **`onFilesChanged` is not the upload seam.** Where a file is stored is `SurveyOptions.uploadFiles`, because only the host knows; this is the notification the answer changed, which anything may watch — a partial save, an audit log, a second view of the same response. A host that conflated them would find its storage called twice the day something else wanted to know. A failed upload announces nothing, because the answer did not change and a listener told otherwise would save a reference to a file nobody stored; a successful one reports **what the host gave back** rather than what went in, since the reference it minted is the thing anything downstream can use. The demo subscribes the way a real host does — no renderer, no callbacks through props — and prints what arrives |

## §B — Expressions & conditional logic

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| B1 | Expression language: literals, `{question}` refs incl. composite paths (`{matrix.row.col}`, `{panel[0].q}`), arithmetic, comparison, and/or/not, contains/anyof/allof, empty/notempty | ☑ | `parity/B1-expression-grammar` (precedence/associativity via print round-trip) + `parity/B1-operators` (evaluation), unit, through public API. Not demo-testable: precedence, associativity and error recovery have no user-visible surface — the demo exercises the language's *use* in every other scenario |
| B2 | Built-in function library (iif, sum, avg, min, max, count, age, today, currentDate, getDate, diffDays, ...) + custom sync and async function registration | ☑ | `built-in function library` for the library, `parity/B2-async-functions` (unit + demo) for registration. Building this found that **a host had no way to register a function at all** through `parseSurvey` — the sync half was reachable only by calling the evaluator directly, which no host does — so both halves now arrive through the parse options. The evaluator stays synchronous: an expression is evaluated inside a dependency transaction, and one that stopped to await would leave every rule after it unevaluated and the model part-way through a cascade. So an async call yields `undefined` this time round — which every operator already treats as an unanswered question, so no operator needed a third state — the work starts, and the rules run again when it lands. **The result cache is load-bearing, not an optimisation**: without it each re-evaluation starts the call again and each call triggers another re-evaluation, and the mutation proving that hung the harness rather than failing it. Keyed on name *and* arguments. A rejection is reported at the call site's own span and not retried, so a broken endpoint is not a request storm. One namespace, checked in both registration orders. **Worth knowing:** every async function is called once at startup with whatever its arguments are then, so a lookup that costs something should return early for an argument it cannot use — the demo's does |
| B3 | `visibleIf` on questions, panels, pages, and individual choices | ☑ | `parity/B3-visible-if`, `parity/B3-visible-if-choice` (questions, pages, choices) and `parity/E1-panel-visibility` (panels, unit + browser + host E2E). A hidden panel takes its subtree out of reach without marking each child invisible — reachability and visibility are different questions, and only the first one is the container's to answer |
| B4 | `enableIf` / `requiredIf` | ☑ | `parity/B4-enable-if`, `parity/B4-required-if` (unit, browser, host E2E). Scope of `requiredIf`: questions, the only element that holds an answer. `enableIf` now also applies to panels, proven by `parity/E1-panel-enable` — the renderer uses a `fieldset`, so a disabled group freezes its subtree natively rather than by walking children |
| B5 | `setValueIf` + `setValueExpression`, `resetValueIf`, `defaultValueExpression` | ☑ | `parity/B5-default-value-expression` (unit + host E2E), `parity/B5-set-value-if` and `parity/B5-reset-value-if` (unit + host E2E). Precedence reset > set > default is defined in `createValueRule`, not left to graph ordering |
| B6 | Calculated values (survey-level `calculatedValues`, usable in expressions and completed HTML) | ☑ | `parity/B6-calculated-values` (unit + host E2E) covers computation, chaining, use from question expressions, and `includeIntoResult`; `parity/B6-calculated-values-in-completed-html` (unit) and `parity/E5-completion-flow` (demo) close the completed-HTML half, which had nowhere to be proven until E5 existed. A completed page reads a calculated value and an answer through the same placeholder and cannot tell them apart — including a value *not* marked `includeIntoResult`, because what an ending says is a different question from what gets submitted |
| B7 | Triggers: complete, setvalue, copyvalue, runexpression, skip | ☑ | `parity/B7-trigger-complete`, `-setvalue`, `-copyvalue`, `-runexpression`, `-skip` (unit); host E2E for all five. Triggers fire on the transition into true, not while it holds. `skip` became demo-testable once the renderer paginated (§E2): `parity/B7-trigger-skip` moves the respondent back a page and the renderer follows |
| B8 | Dependency graph: value change re-evaluates only dependents; cycles detected and reported | ☑ | `parity/B8-dependency-graph` (selective re-evaluation, ordering), `parity/B8-cycle-reporting` (participating nodes named), `parity/B8-pattern-edges` (dynamic collections), unit, through public API. Not demo-testable: "only dependents re-evaluated" is by definition invisible, and proving cycle reporting would mean authoring a broken survey into the demo |
| B9 | Carry-forward choices (`choicesFromQuestion`, selected/unselected modes) | ☑ | `parity/B9-carry-forward-choices` (unit + host E2E). The carried list is a live view, not a snapshot, so a source choice hidden by its own `visibleIf` disappears here too. Shares `ChoiceSourceController` with B10, so both dynamic sources resolve through one object |
| B10 | REST choices (`choicesByUrl`: url/path/valueName/titleName, caching, url with `{question}` placeholders) | ☑ | `parity/B10-rest-choices` (unit + host E2E). Placeholders become real graph dependencies, so an answer change re-fetches. The fetcher is injected — core is I/O-free and cannot reference `fetch`. The demo calls a live public API; the E2E intercepts it so CI never depends on a third party. A superseded response cannot install itself over a newer one (request generations, proven by mutation), the cache is keyed on the conversion settings and not the URL alone, and one in-flight request is shared by every source awaiting it. The original typed value survives the renderer, so a numeric `id` records as a number. Definitions carry origin-relative URLs and the host resolves the origin in `fetchJson`, so one definition promotes across environments unedited ([ADR-0017](./adr/0017-choices-url-environment-portability.md)); the demo's absolute URL demonstrates a public third-party API, not deployment portability. **Gaps noted:** the model carries no loading flag, so a renderer cannot show a loading state; multi-origin definitions are B11 |
| B11 | Deployment variable scope: `{@name}` placeholders resolved from host-supplied endpoints, distinct from the answer scope | ☑ | `parity/B11-deployment-scope` (unit). Built to [ADR-0017](./adr/0017-choices-url-environment-portability.md): substituted **verbatim** because it is a URL prefix and not a value, while an answer in the same URL is still percent-encoded — opposite treatment on purpose, since an encoded origin is a broken request and an unencoded answer is a way to reach a different host. Never a graph dependency: it is constant for the session. A separate namespace, so collision with a question name is impossible by construction. An undeclared name is a **parse diagnostic at error severity** — and, a test found, that alone was not enough: substituting the empty string left `/users`, which the fetcher then sent to the app's own origin, so a URL naming an origin nobody supplied is now not fetched at all. The template round-trips; the resolved origin never serializes. **Unproven guard:** the filter keeping `{@name}` out of the dependency graph. Its effect is a graph node that never fires, which has no observable behaviour — the mutation removing it survives, and inventing a test that could see it would be testing the test |

## §C — Question types: core

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| C1 | text — all inputTypes (text, number, email, date, datetime-local, time, tel, url, color, range, password), min/max, step, ~~maskSettings~~ | ☑ | `parity/C1-input-types`, `parity/C1-text-bounds`, `parity/C1-numeric-answers-are-numbers` (unit + demo) cover every input type, `min`/`max`/`step`, and the rule that a numeric input stores a number rather than the string the DOM reported. **`maskSettings` is dropped from parity scope**, not deferred ([ADR-0018](./adr/0018-input-masking-out-of-scope.md), 2026-08-02): masking is a caret-management problem wearing a formatting problem's clothes, the model already owns the part that matters — what reaches `data` is a typed value either way — and a host that needs one plugs in a library through the renderer seam rather than taking a nearly-right implementation from us. This is the **first named gap against the SurveyJS Form Library**, and it is stated here rather than implied by a row that looks complete |
| C2 | comment (multi-line, autoGrow, character counter) | ☑ | `parity/C2-comment` (unit + demo), `parity/C2-comment-auto-grow` (demo, measuring real height in Chromium). The budget is enforced by the model, not just displayed: a trigger or a restored `data` payload can exceed a `maxlength` attribute |
| C3 | radiogroup (choices, otherItem, noneItem, showClearButton, colCount, choicesOrder) | ☑ | `parity/C3-radiogroup` (unit), `parity/C3-C4-select-questions` (host E2E), browser proof for selection. `choicesOrder` supports none/asc/desc; random is deferred as it would make the suite non-deterministic |
| C4 | checkbox (selectAll, none, other, maxSelectedChoices, colCount) | ☑ | `parity/C4-checkbox` (unit), `parity/C3-C4-select-questions` (host E2E), browser proof for multi-select |
| C5 | dropdown (search/filter, lazy loading, placeholder, showOtherItem) | ☑ | `parity/C5-dropdown` (unit + browser) for single-select, placeholder and showOtherItem; `parity/C5-lazy-loading` and `parity/C5-lazy-search` (unit + demo) for paging. The host supplies a `loadChoicePage` loader — a callback rather than a URL template, because paging needs an offset, a size and a term against an API only the host knows the shape of, and core carries no I/O. Pages **accumulate**: the respondent is looking at page one, and a list that emptied itself to show more would lose their place. The end of the list is what the host reports rather than what a short page implies — a server-side match can legitimately be thin — and a mutation that inferred it from the page length is killed by a loader that under-fills. Search goes to the host, because the matching entry may never have been loaded; a reply for a term the respondent has typed past is discarded, proven by answering the requests out of order. A page that fails to arrive leaves the list usable and retryable rather than loading forever. Pagers outlive rule registration, which is rebuilt whole on every tree change. **The scroll trigger is an explicit control, not a sentinel**: a native `<select>` has no scroll to observe and infinite scroll reaches nobody who is not pointing at the list — Phase 2's combobox adds the scroll trigger alongside the button, never instead of it. The searchable combobox *UI* stays deferred to that a11y pass; the filter is a labelled search field beside a native list |
| C6 | tagbox (multi-select dropdown with search + lazy load) | ☑ | `parity/C6-tagbox` (unit + browser in real Chromium, proving the native adapter preserves the model's invariants) and `parity/C6-lazy-tagbox` (unit). The adapter reports its whole selection and the model decides what that means, so none-exclusivity and `maxSelectedChoices` hold however the selection was made. Paging lives on `SelectQuestion` rather than on either subclass, so a tagbox pages on identical terms — and an answer survives a filter that hides the choice naming it, because what someone chose is not a function of what the list is currently showing. The DOM half is C5's: one renderer is registered for both types. The combobox UI is deferred with C5 |
| C7 | boolean (switch + radio render modes, labelTrue/False, valueTrue/False) | ☑ | `parity/C7-boolean` (unit), `parity/C7-boolean-switch` and `parity/C7-boolean-radio-with-custom-values` (demo). Unanswered is a third state, not `false`: "was never asked" and "did not agree" are different facts and only the model can keep them apart |
| C8 | rating (numeric, stars, smileys, rateValues, min/max descriptions, display mode auto-switch) | ☑ | `parity/C8-rating` (unit), `parity/C8-rating-stars` and `parity/C8-rating-auto-collapses-a-long-scale` (demo). Stars and smileys are `aria-hidden` decoration over real radios, so the scale announces "4" rather than "star star star star"; `auto` collapses at eleven steps, and the collapsed form is a labelled control rather than a group so the select has a name of its own |
| C9 | ranking (drag reorder, selectToRankEnabled, keyboard support) | ☑ | `parity/C9-ranking`, `parity/C9-select-to-rank`, `parity/C9-reorder-primitive` (unit); `parity/C9-keyboard-reorder` (browser, in real Chromium); `parity/C9-drag-reorder`, `parity/C9-keyboard-reorder`, `parity/C9-select-to-rank` (demo, with a real pointer drag). Built as a **reusable interaction** rather than as ranking code, per [ADR-0009](./adr/0009-creator-drag-and-drop.md) constraint 3: `moveWithin` is the list arithmetic in core, `useReorder` the pointer-and-keyboard adapter in `@kajay/react`, and neither knows what is being reordered — Phase 3's Creator extends this instead of introducing a second drag system. Pointer events throughout, never HTML5 drag-and-drop, which has no keyboard story. The model is updated *during* a drag, so what is on screen mid-gesture is the answer as recorded rather than a preview that could disagree with it. Space or Enter picks a row up, the arrows move it, Escape puts it back, and every step is announced with its position and the total — a row sliding past its neighbours is otherwise entirely invisible. Mutation proved the arrow keys must be claimed (an unclaimed arrow scrolls the page out from under the respondent) and disproved an explicit refocus, which changed nothing because React already moves the focused element when rows are keyed by identity. An untouched ranking records **no answer**: the presented order is the author's, and banking it as agreement would put an opinion in the data that nobody expressed. **Unproven guard:** the pointer-id check that stops a second finger ending someone else's drag — there is no multi-touch harness here to demonstrate it |
| C10 | imagepicker (single/multi, imageFit, contentMode image/video) | ☑ | `parity/C10-imagepicker` (unit + demo). The one select type whose **arity is a property** rather than its type — everywhere else the split is a design-time fact, which is why those semantics live in two base classes. `applySelection` is the single point where the switch happens; a `select` override alongside it changed nothing, which a mutation test proved by surviving its removal. The choice text is every tile's accessible name whether or not `showLabel` draws it: a grid of unlabelled pictures is not an answerable question for anyone who cannot see them |
| C11 | multipletext (items, itemSize, per-item validation) | ☑ | `parity/C11-multipletext`, `parity/C11-multipletext-per-item-validation` (unit + demo). The answer is one object under the question's name, so `{address.city}` reaches a single field with nothing added — the path resolver already walks dotted references. Errors carry a `path` naming the field that earned them, which is what lets a renderer put the message beside the input instead of prefixing every line with a label the field already shows; §F's matrix cells want the same — and now use it. **Two defects surfaced while building F1**, both fixed here: an untouched multipletext reported none of its required items (the question was empty, so the check stopped before reaching them), and a message reported against the question as a whole had no slot to render into. Both are pinned by named tests |
| C12 | html (display), image (display), expression (read-only computed with displayStyle/format) | ☑ | `parity/C12-display-elements`, `parity/C12-expression-question` (unit); `parity/C12-html-and-image`, `parity/C12-expression-question` (demo). `html` and `image` descend from a new `displayelement` base rather than from `question`, so the Creator's generated property grid never offers `isRequired` on a paragraph of text. **Markup is rendered as markup** — that is the feature — so a definition is code at the host's level of trust; a host taking definitions from untrusted authors passes `sanitizeHtml` to `<Survey>`, and none ships here because a sanitizer that is nearly right is worse than none. `expression` formats through a fixed `en-US` locale so the same definition reads the same everywhere; making that follow the survey locale is §J |

## §D — Validation

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| D1 | Required with custom `requiredErrorText`; `isRequired` on any type incl. matrix rows | ☑ | `parity/D1-required` (demo + browser + unit) for every question type; `parity/F1-matrix-required` (unit) for matrix rows, where `isAllRowRequired` demands each visible row and the authored `requiredErrorText` applies to the row, because the row is what asked for an answer. `requiredIf` reaches the same gate as `isRequired`. ## §E — Navigation, flow & state

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| E1 | Pages, panels (nested, collapsible, visibleIf), elements ordering | ☑ | `parity/E1-panels`, `parity/E1-panel-visibility`, `parity/E1-panel-enable`, `parity/E1-panel-collapse` (unit, browser, host E2E). Panels nest arbitrarily and round-trip. A page is deliberately **not** a page element — parenting it under the same base would have made a page a legal child of a page, which the contract caught. Collapsing lives on the model, not in React: the definition declares the starting state and the Creator has to edit it. Only a panel that authored `state` is collapsible; one left at the default is a grouping device, and a toggle would invite hiding content the author never meant to hide |
| E2 | Prev/next/complete flow; page visibility recalculation; questionsOnPageMode (standard, singlePage, questionPerPage) | ☑ | `parity/E2-navigation`, `parity/E2-page-visibility`, `parity/E2-questions-on-page-mode` (unit, browser, host E2E). Every index counts **visible** pages, so a hidden page is not somewhere a respondent can stand. Hiding the page underneath a respondent clamps to the last visible one and announces the move, rather than leaving the renderer drawing nothing. `questionsOnPageMode` reshapes what navigation and the renderer see while leaving the authored `pages` untouched, and the reshaped list is memoised on its structure so React does not remount every question per render |
| E3 | Progress bar (pages, questions, correct-answer variants) + TOC navigation | ☑ | `parity/E3-progress`, `parity/E3-progress-correct` (unit), `parity/E3-progress`, `parity/E3-progress-correct` (browser), `parity/E3-progress-and-toc` (demo). `showProgressBar` (off/top/bottom/both), `progressBarType` (pages/questions/requiredQuestions/**correctQuestions**) and `showTOC`. Measurement is a **pure function over the survey** exported from core, so the renderer gained no model surface and the arithmetic is testable without a DOM. `pages` counts what is **behind** the respondent — the page they are looking at is not finished, and the flattering alternative tells someone they are done with a page of questions still in front of them. Unreachable questions are not in the total, or progress would fall as branches opened. Nothing to answer counts as nothing outstanding, because an empty bar on a form that cannot be advanced is the more misleading lie. A native `<progress>` with a text label, since "two thirds" is a shape and "2 of 3 pages completed" is the fact that survives being read aloud. The TOC is a labelled `<nav>` of buttons with `aria-current`, and jumping **does not run the validation gate** — a contents list is for looking around, and refusing to let someone glance at page four because page two is incomplete makes it useless exactly when it is most wanted. The correct-answer variant closed with E8: it reads `scoreQuiz`, counts **marks** rather than questions, says "1 of 2 correct" rather than "completed" — these are earned, not done — and is the only one of the four that can go *down*. Closing it found a defect in the other three: **nothing subscribed the bar to answers**, so a question-counting bar held its first reading until a page turn or a rule forced a render. The subscription sits on the bar, not the form, or one number would re-render every question on the page per keystroke |
| E4 | Preview mode before complete (showPreviewBeforeComplete, edit-from-preview) | ☑ | `parity/E4-preview` (unit + browser + demo). Preview is a **survey state**, not a flag beside the others, and that is what makes it read-only by construction: the survey reports itself read-only while previewing, so every question already is and no renderer is told to make it so — a mutation removing that one clause is killed by the model, not by the DOM. It draws the real question renderers rather than a summary table: an answer shown in a different control from the one it was given in invites a misreading, and a table needs its own formatting per question type, which is where the table and the form start to disagree. The last page's validation gate runs **before** the preview, so nobody reviews answers the survey is about to refuse. Edit returns to the page they left rather than the first one — a preview that costs a respondent their place is one they learn not to open. `showAnsweredQuestions` leaves out what nobody touched, and unreachable questions are never reviewed because they were never asked. A `complete` trigger still ends the survey outright: it says complete, not "ask them again" |

The renderer's whole part is putting that map on one element and letting it inherit, which is why **`@kajay/react` never imports `@kajay/themes`** (the architecture check forbids it) and why two surveys on one page can be themed differently. **What a theme does not name, it does not set**: an absent field leaves the stylesheet's default alone rather than overwriting it with a guess, which is what stops a partial theme becoming a broken one. `panelless` is expressed as two lengths rather than a mode flag, so no rule branches on it. A backdrop is its own layer, so its opacity applies to the picture and not to the text in front of it. `variables` is the escape hatch and wins over everything computed
| I3 | Preset themes incl. light/dark in `@kajay/themes` | ☑ | `parity/I3-presets` (unit + demo). Light, dark and panelless, each naming a **full** palette — a preset that left a colour out would inherit whatever the last theme set, which is exactly how switching themes leaves one wrong colour behind, and a test enumerates them to prevent it. Both delivery routes are proven: the CSS preset (`@kajay/themes/themes/dark.css`, exercised from an installed tarball by the pack test) and the runtime object, switched live in the demo
| I4 | Per-instance css class overrides (survey-level css merge) | ☑ | `parity/I4-css-overrides` (browser + demo). Classes are **added to the built-in names, never substituted for them**: replacing them would take the shipped stylesheet with it and leave a host who wanted one extra class reimplementing everything. Supplied per `<Survey>` rather than in the definition, because a class name is a fact about one host's stylesheet and not about the survey. A part nobody named is left exactly as it was, so a partial override cannot blank the rest. Every page element goes through one wrapper, which is why the host's class reaches question types the library has never heard of |
| I5 | Responsive layout: startWithNewLine, colCount, question width/minWidth, title alignment options | ☑ | `parity/I5-layout` (browser ×4 + demo). Pages and panels lay out as grids, so `colCount` reaches CSS as `--kajay-col-count` rather than as a class per count — an author may ask for any number and a stylesheet cannot enumerate them. `startWithNewLine` is a **grid start on the element that wants the break**, not a break element in the tree that would mean nothing to a screen reader. It **defaults to false**, a deliberate divergence from SurveyJS, where the true default makes `colCount` do nothing until every question on the page is edited: the layout an author asks for should be the one they get. `width` and `minWidth` are CSS lengths on the same wrapper, and `titleLocation: hidden` is **visual only** — the title is clipped but still names the input, because a field with no accessible name is unanswerable to anyone who cannot see the column header above it. All four live on one wrapper per page element, which is why none of the twenty-odd renderers had to learn a layout rule |
| I6 | Custom rendering seams: register custom renderer per question type; markdown/HTML in titles via onTextMarkdown | ☑ | `parity/A4-custom-question-renderer` (browser) proves a host-registered renderer through the public React seam, which [ADR-0019](./adr/0019-deep-runtime-modules-and-rendering-seam.md) made one dispatch table for questions, panels, display elements and custom types alike; `parity/I6-text-seam` (browser + demo) closes the other half. The text seam **returns a node, not an HTML string**. A host that wants markdown renders it themselves, with their own sanitizer, and the library never inserts markup it did not build — the same boundary `sanitizeHtml` draws for the `html` element, arrived at from the other side. It is told *which* piece of text it is being asked about, so a host can allow emphasis in a description and refuse it in a label without inspecting the string. **No markdown parser ships here**: shipping one would ship its escaping rules and its vulnerabilities with it. The demo implements the smallest thing that could be called markdown, to prove the seam rather than the syntax |

## §J — Localization & accessibility

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| J1 | Localizable strings: every user-facing property accepts `{ default, <locale> }`; survey.locale switch re-renders | ☑ | `parity/J1-localizable-strings`, `parity/J1-localizable-reach`, `parity/J1-localized-round-trip` (unit); `parity/J1-locale-switch` (browser + demo); `localized-strings-round-trip` ([conformance v1](../conformance/v1/definitions.json)). Thirty-five properties are marked `isLocalizable`, and the flag is **declared rather than inferred from the type**: `title` is prose and `visibleIf` is code, and both are `string` — an object on the second is still a type error, because translating a condition breaks the survey in whichever language somebody translated it into. **The definition stores the object as authored.** Resolving on the way in would flatten a survey to one language the first time anyone read it, and the fixed-point rule would not catch it: both passes would agree and every other translation would be gone. Resolution happens in `getStringProperty` — *one* method — which is why ninety-odd call sites read titles, placeholders and messages in the current locale without one of them learning that a title can be an object. The locale is a **shared mutable holder handed out during parsing**, not walked in afterwards: parsing is the only place that sees every element, and a walk would have to know each child collection separately and be wrong about the next one — choices, validators and multiple-text items are exactly the three it would have missed, and a test names them. Fallback is locale, then base language (`fr-CA` → `fr`), then `default`; without the middle step a French-Canadian respondent reads English in a survey that *was* translated into French. A definition's `locale` is the one it **opens** in and a runtime switch never serializes, on the same rule that keeps `visibleIf`'s current answer out. Switching rebuilds repeating instances, because a cell title is composed at build time from the template's resolved one — the only translated string the model caches, and a surviving mutant is what proved it needed throwing away. The renderer re-renders from one subscription at the survey root: a locale switch changes every string at once, so per-question listeners would be a thousand subscriptions agreeing on the same answer |
| J2 | UI string dictionaries with runtime registration; `en` complete; ≥3 seed locales proving the mechanism | ☑ | `parity/J2-string-catalogue`, `parity/J2-string-dictionary`, `parity/J2-messages-are-localized` (unit); `parity/J2-ui-strings` (browser + demo). Every string the library itself says — validation messages, navigation labels, the ranking hints, the file and timer panels — goes through a key. **`en` is complete by construction**: the catalogue carries the English text, so `EN_STRINGS` is built from it and a key can only exist by having its English written beside it. That follows ADR-0020's pattern for diagnostic codes, and it means the claim is a fact about the build rather than a line in a document; using a key that does not exist fails to compile. Three seed locales (fr, de, es), complete rather than partial — a partial seed would prove the fallback instead of the mechanism, and the fallback has its own test. They are **seeds, not shipped translations**: breadth here is a community model by design, and a deployment that cares about its French should review the file rather than trust it. **One dictionary per survey, not one per process**: the metadata registry is global by design and the suite pays for it in care, and there is no comparable reason here — a host serving two tenants must be able to word them differently. Registering merges, so overriding one string does not blank the other fifty, and a host can add a language nobody shipped (the demo adds Welsh). The last-resort fallback is the **registered** English rather than the shipped constant, which a failing test caught: a survey naming no locale at all — most of them — was silently ignoring every English override. The dictionary hangs off the same locale scope J1 already put on every element, which is what lets a validator inside a matrix cell speak the respondent's language without being handed the survey. **Not covered:** languages with more than two plural categories. English needs two forms and picks by count, and the progress labels are two keys for that reason; Polish, Russian and Arabic need a plural *rule*, which is a formatter a host supplies. Stated rather than approximated, because confidently wrong grammar is worse than an obvious gap |
| J3 | RTL support | ☑ | `parity/J3-rtl` (unit + browser + demo). **A `dir` attribute and nothing else.** The browser already mirrors layout, reorders bidirectional text and resolves logical CSS properties; a stylesheet doing any of that by hand would be a second copy of the first, wrong wherever nobody read. The whole change to `@kajay/themes` was five declarations — `text-align: left` became `start`, `padding-left` became `padding-inline-start` — because the sheet was already logical everywhere else, and a header now says why it must stay that way: a rule saying `left` is a bug in Arabic that nobody sees while reading English. **Direction is derived from the language**, not a separate flag: it is a fact about a script, and an author who translates a survey into Hebrew should not also have to remember to flip a switch — one who forgets would ship a survey laid out backwards. `textDirection` overrides for what the list cannot know: a private locale tag, or a survey deliberately laid out against its language. A hard-coded list rather than `Intl.Locale.getTextInfo`, which is not in every supported engine and would guess left-to-right on exactly the engines least likely to be tested. Scoped to the survey rather than the document, so a survey embedded in an English page may still be in Arabic and two surveys on one page may read different ways. The `dir` sits on the same wrapper the theme variables do — one element scoping everything that is true of *this* survey rather than of the page |
| J4 | Keyboard operability for every question type incl. ranking and matrices | ☑ | `parity/J4-keyboard` (demo, six scenarios). Real keys throughout: `focus()` only ever puts the cursor at the *start* of a journey, and nothing clicks its way to the state it is about to assert. The types that could have failed are the ones not built from a plain input, and each is proven separately — a **star rating** arrows between values because the glyph is `aria-hidden` decoration over a real radio (`getByLabel` finds nothing there while `getByRole('radio')` finds it, which is the distinction); a **matrix** arrows *along a row*, because each row is its own radio group and one group across the table would let a single arrow press walk into another question; a **ranking** is picked up, moved and dropped with space and the arrows, and focus stays on the row that moved so a respondent does not lose their place; a **repeating panel** adds an instance on Enter. Enter in a text field advances the page, which is the form's submit rather than anything the renderer added |
| J5 | ARIA roles/labels/error associations; axe checks pass on every demo page | ☑ | `parity/J5-axe` (demo, seven sweeps) against `wcag2a`, `wcag2aa`, `wcag21a` and `wcag21aa`: all three pages, a page showing its errors, the preview, the completed page, right-to-left, and the dark theme. Scoped to the survey — the diagnostic JSON panels around it are the demo's own scaffolding, and failing the suite for the demo's chrome would train everyone to ignore it. It found a real defect on its first run: **the shipped dark preset's primary button was white on a light accent at 2.51:1**, a control nobody with low vision could read, in the one theme least likely to be checked by someone developing in the light one. The fix is a token — `--kajay-color-on-accent` — because what sits *on* the accent does not follow from the accent: a dark theme lightens the accent so it shows against a dark surface, and that is exactly when white stops working. Contrast is a property of the palette, so the sweep runs once per shipped theme rather than once per survey. **axe is a floor, not a ceiling** — it checks names, roles, structure and contrast, and cannot check whether the survey is *operable*, which is why J4 walks the hard types with nothing but a keyboard |

## §K — Creator: design surface & toolbox

| ID | Feature | Status | Proof |
| --- | --- | --- | --- |
| K1 | Toolbox listing all registered types (auto-populated from registry), search, categories, custom toolbox items | ☑ | `parity/K1-toolbox-registry`, `parity/K1-toolbox-search`, `parity/K1-toolbox-custom-items`, `parity/K1-toolbox-changes` (unit); `parity/K1-toolbox` and `parity/K1-primitives` (browser); `parity/K1-toolbox` (demo, including an axe sweep and a theme check). **Nothing in `Toolbox.ts` lists a type.** The items come from `getConcreteSubclasses('pageelement')` — not `question`, because a panel and an image are things a designer drops on a page and are not questions — and `builtInToolbox.ts` says only what they are *called* and which drawer they are in. A type that table has never heard of still appears, under a fallback title in "Other": auto-population is not a courtesy extended to types somebody remembered to list, and a test registers one to prove it. Titles and categories live in the Creator rather than on the class descriptor, because "which drawer" is a decision about a designer and the registry is the runtime's — a survey being answered on a server has no drawers. **`name` is the identity, not `type`**, so one type can appear more than once: "Rating (stars)" and "Rating (smileys)" create the same type and differ only in the `defaults` they start it with, which is also exactly the shape a host adding a custom item reaches for. Adding an existing name *replaces* it, because curation is the same act as addition — and a retitled item keeps the keywords it had, or renaming the dropdown would silently stop "select" from finding it. Search covers the title, the type (a definition author knows `paneldynamic`, not "Repeating panel") and the keywords, and a category left empty is not drawn. The model is **stateful** because the search term is designer state ([ADR-0021](./adr/0021-creator-composition.md)) and the panel holds none; the panel reads a version counter rather than the categories, since `categories` builds a fresh array per read. Picking is **reported, never performed** — where an item lands is K2 and K3, and a toolbox that reached into a survey would be the second thing deciding it. This is also the first use of the primitive seam ([ADR-0022](./adr/0022-design-system-primitives.md)): the panel draws through `Button` and `Input`, a host may replace either, an explicitly `undefined` entry means "use the default" rather than "draw nothing", and the map's partiality is proven by replacing one and leaving the other. The demo applies the theme variables to its own section rather than the panel taking a `theme` prop — the tokens are CSS custom properties and any element a host controls can carry them |
| K2 | Drag-drop from toolbox onto surface; reorder questions/panels/pages by drag; drop indicators | ☐ | Partial: dropping from the toolbox, reordering questions and panels, and drop indicators are done; dropping *into* a panel is not, for the reason at the end of this row. Reordering pages by drag landed with K4, through this row's own placement model. `parity/K2-slots`, `parity/K2-placement`, `parity/K2-move`, `parity/K2-placement-refusals`, `parity/K2-place` (unit); `parity/K2-keyboard`, `parity/K2-indicator`, `parity/K2-announce`, `parity/K2-handle` (browser); `parity/K2-drag`, `parity/K2-toolbox` (demo). [ADR-0009](./adr/0009-creator-drag-and-drop.md) was deferred to this row and is decided here: **hand-rolled, no library.** Constraint 2 had already removed the cheapest option, and what was left of the case for a library was thin — the expensive part of drag-and-drop is the keyboard grammar and the live-region vocabulary, which Phase 1 already paid for in `useReorder`; adopting one now would mean auditing *its* keyboard story against J4 and J5 instead. A library that owns a portal and a drag layer is also a second opinion about the Creator's markup, underneath a decision we had just made to leave that to the host (ADR-0021, ADR-0022). **The model is a list of insertion slots, not element indices.** A slot is a container and an index, so *n* elements offer *n + 1* of them — which makes a toolbox drop and a reorder the same operation (differing only in whether the thing exists yet), makes the drop indicator a model value rather than a pixel, and makes the keyboard story a walk rather than a second gesture to learn. **Structural edits are definition-in, definition-out, re-parsed**, while property edits stay in the model. Adding an element correctly means a name nothing has taken, a value host, layout and a place in the logic graph — which is what `parseSurvey` is, and re-implementing it incrementally is how the Creator becomes the only place a survey can reach a state the parser would never produce. Three things follow, all wanted: K6 inherits a stack of definitions rather than a command per operation; every drop exercises [ADR-0002](./adr/0002-round-trip-fixed-point.md)'s fixed point; and element identity does not survive an edit, so the selection is re-resolved by name. **A Creator drag previews and commits once** — the opposite of C9's ranking, which applies every move live. Applying per pointer-move would re-parse the survey and rebuild the canvas under the designer's pointer, destroying focus on every keystroke of a keyboard drag; and an indicator is a preview by another name, so a model that applies live has nothing to indicate. Escape abandons rather than reverses. **Constraint 3's letter is not met and its purpose is:** `useReorder` is not the vehicle — its contract is one index space where this has two, and it applies live where this previews — but the grammar is identical down to the sentences, with `reorderAnnouncement` exported and reused, so a designer who has used a ranking question already knows this. **Dragging is on a handle, not the element**, because the arrow keys already mean something inside a radio group, a rating and a ranking list, which is most of §C. A press does not begin a drag: the first *move* does, or focusing a handle would announce a placement grabbed and instantly abandoned. The toolbox item's click is owned by the placement rather than the toolbox, because a drag ends in a click and a toolbox that appended on its own put two questions on the page for one gesture. Slot geometry is nearest-centre then which-side-of-it, along whichever axis the pointer is further out on, so it reads as above/below in a column and left/right in a `colCount: 2` row — proven in the demo, which is two columns. Eleven mutants die, including the reorder off-by-one, which first **survived** a test that moved to the end of the list where an index past the end and one before it slice identically. **The gap is named:** dropping *into* a panel is not supported. The surface adorns only a page's top-level elements, because a panel is drawn by the respondent's own panel renderer and its children sit in markup the Creator does not own; making a nested element addressable is a change to how the surface renders, not to how placement works. The slot model already reads correctly for a panel and deliberately does **not** produce slots nothing can reach — E7 taught that lesson expensively |
| K3 | Live design surface rendering real questions (WYSIWYG via @kajay/react), selection, inline title editing | ☑ | `parity/K3-design-surface`, `parity/K3-design-mode` (unit); `parity/K3-design-surface`, `parity/K3-selection`, `parity/K3-inline-title` (browser); the same three plus an axe sweep (demo). The questions are **the real ones**, drawn element by element through the registry [ADR-0019](./adr/0019-deep-runtime-modules-and-rendering-seam.md) already made public — so a question type the Creator has never heard of renders correctly and nothing here knows what a radio group is. Each sits in `PageElementSlot`, the renderer's own layout wrapper, now exported for this: `colCount`, `width` and `startWithNewLine` mean on the canvas exactly what they will mean to a respondent, and re-writing that wrapper here would put I5's decisions in a second place to drift from the first. **The survey is put in design mode**, a third contributor to `isReadOnly` beside the authored property and E4's preview — runtime state, never serialized, because `setReadOnly` writes into the definition and a Creator that reached for it would stamp every survey it opened with a flag the author never wrote. That is what stops a click answering, through E7's existing refusal rather than anything new. Selection has two paths deliberately: a click anywhere selects, and the adorner carries a real `<button>` because a click is not a keyboard. Clicking the background clears it, guarded on the event target — without that guard the capture-phase select was immediately undone by the same click bubbling up, and nothing could be selected at all. Every edit goes through one `change` chokepoint, which is what K6's undo stack will wrap. **Editing a localized title edits it in place**: a title authored as `{ default, fr }` keeps every other language, because overwriting it with a plain string would drop them the moment somebody fixed a typo and nothing about typing in a box suggests that. **Departure from "inline":** the title editor sits in the adorner and the rendered question keeps its own title, so a designer sees both — the field they are editing and the label a respondent will read, updating live. An editor drawn *over* the rendered title would have to guess at its position, and one that suppressed it would make the layout on screen a lie |
| K4 | Page management: add/remove/reorder pages, page adorners | ☑ | `parity/K4-add-page`, `parity/K4-remove-page`, `parity/K4-landing`, `parity/K4-page-surface`, `parity/K4-reorder-pages` (unit); `parity/K4-navigate`, `parity/K4-add-page`, `parity/K4-remove-page`, `parity/K4-reorder-pages`, `parity/K4-page-adorner` (browser); the same plus an axe sweep (demo). **Reordering pages needed no second drag implementation.** K2's `DropSlot` gained a `list` — the survey's pages, or a page's elements — and everything else was already right: the same `applyPlacement`, the same off-by-one moving downwards, the same pair of slots that mean "where it already is", the same keyboard grammar and the same sentences in the live region. That off-by-one had already **survived a mutant once**, which is the whole argument against a second copy of it. One placement now drives two lists, so each indicator checks that a slot is aimed at *its* list — and the first two tests of that could not tell the difference, because the slot indices in them could never collide. Both mutants survived until the tests were rewritten to aim a page drag at a slot number the canvas also has an element at. **Add, remove and go-to are not placements**, and are modelled separately: nobody drags a page into existence, and nothing in the toolbox is a page. Adding appends and *opens* the new page, because a designer adds one in order to put something on it. **Removing takes the questions with it** — that is the operation, not a side effect, and K6's undo is what makes it safe to mean. **The last page can go**: refusing would mean a designer cannot delete a page they do not want without first adding a replacement, and a survey with no pages is the state every new one starts in, which the canvas already renders and says so. The canvas lands on the page that took its place, or the one before it when the last went — but only when the page removed was the one being looked at, which a surviving assertion caught. Switching page clears the selection, because leaving it would have the property grid editing something off screen. Page names come from the **survey-wide** pool, since `{page1}` in an expression has to mean one thing. **Page adorners, in both senses:** a `PageNavigatorPanel` piece (ADR-0021) listing every page with `aria-current` on the open one — not colour alone — plus move and delete; and a header on the canvas itself, which is where a page finally becomes *selectable*. K3 could select every element except the one containing them. Its title editor sits beside the heading rather than over it, K3's decision applied to the element K3 could not reach; an untitled page is listed by its name, greyed, because a blank row would be unreachable by voice or by screen reader even though a page without a title legitimately renders without one (E1). **A found defect, fixed here:** the drop indicator drew on slots the model would refuse — the position an item already occupies — promising a move it was about to decline. The keyboard never reaches that state because the arrows step over it, so only a pointer could find it, and only an E2E scenario could prove it. Eleven mutants die |
